### 1순위: 대량 보상 집계 처리

1,000회의 보상 결과를 아이템별로 먼저 집계한 후 다음 작업을 한 번만 수행하도록 변경하는 것이 필요합니다.

- 기존 스택의 여유 수량 계산
- 필요한 신규 슬롯 수 계산
- 인벤토리 공간 확인
- 아이템 생성 및 예약
- 최종 보상 반영

목표 구조:

```text
현재:
1,000회 × 보상 계산
        × 슬롯 계산
        × 잔여 인벤토리 계산
        × 아이템 예약

개선:
1,000회 보상 결과 생성
→ 아이템별 수량 집계
→ 슬롯 및 잔여 인벤토리 한 번 계산
→ 아이템 종류별 예약 및 반영
```

확률 보상인 경우 단순히 기댓값에 1,000을 곱하면 기존 확률 동작이 변경될 수 있습니다. 보상 추첨 결과는 기존 규칙대로 생성하되, 인벤토리 검사와 지급 처리를 아이템별로 합산하는 방법이 안전합니다.

### 2순위: 잔여 인벤토리 계산 최적화

현재 슬롯 사용량을 인벤토리 타입별 카운터로 유지하면 다음과 같이 O(1)에 가까운 계산이 가능합니다.

```text
남은 슬롯
= 최대 슬롯
- 현재 사용 슬롯
- 예약으로 추가될 슬롯
```

아이템 추가, 삭제 및 이동 시 카운터의 정합성을 유지해야 합니다.

### 3순위: 메모리 할당 제거

잔여 인벤토리 계산 내부의 컬렉션 복사와 임시 객체 생성을 제거해야 합니다. 호출당 할당을 줄이지 않으면 다중 사용자 실행 시 GC에 의한 추가 지연이 발생할 수 있습니다.

### 보조 방안: 청크 처리

근본 개선을 즉시 적용하기 어려운 경우, 대량 보상을 여러 틱으로 분할하면 한 틱의 장시간 점유는 완화할 수 있습니다.

다만 이 방법은 총연산량과 메모리 할당을 줄이지 못하므로 임시 안전장치로 사용하는 것이 적절합니다. Actor 인벤토리 상태의 정합성 문제 때문에 전체 보상 처리를 단순히 다른 스레드로 이동하는 방식은 우선 해결책으로 권장하지 않습니다.

> 재료 상자 1,000개 사용 시 보상 아이템의 기존 스택이 없으면, 각 `GiveReward()` 호출에서 신규 슬롯이 필요하다고 판단하여 잔여 인벤토리 계산을 1,000회 반복한다. 인벤토리 아이템 수가 많은 상태에서는 이 구간에 약 588ms가 소요되고 약 78MB의 추가 메모리가 할당된다. 그 결과 Zone Thread가 약 0.665초 동안 점유되어 동일 Thread에 속한 다른 사용자들의 게임 처리가 지연된다.

## 권장 방식: 실제 인벤토리가 아닌 가상 보상 목록 사용

말씀하신 사전 공간 검사는 좋은 방향입니다. 다만 `count=0` 아이템 대신 임시 Dictionary에 실제 지급 예정 수량을 모으는 것이 안전합니다.

```text
상자 보상 결정
→ 아이템별 지급 수량 집계
→ 필요한 신규 슬롯 수 한 번 계산
→ 공간이 부족하면 사용 전 에러 반환
→ 공간이 충분하면 실제 지급
```

예시 구조입니다.

```csharp
Dictionary<int, long> rewardItemCounts;
```

그 후 기존 시뮬레이션 함수를 한 번만 호출합니다.

```csharp
inventory.GetNeedInvenCountSimualation(
    rewardItemCounts,
    out var needSlotCount);

var remainSlotCount = actor.GetActorInventoryRemainCount();

if (remainSlotCount < needSlotCount)
    return ePacketCommonResult.InventoryFull;
```

이 방식이라면 말씀하신 조건도 정상 처리할 수 있습니다.

```text
남은 슬롯: 1
필요 슬롯: 3
→ InventoryFull 반환
→ 상자와 보상 모두 변경하지 않음
```

```csharp

    rewardItemList[i].count * rewardCount;
```

따라서 가장 수정이 적은 방법은 다음과 같습니다.

- 동일한 `rewardConfirmId`가 1,000번 나온다면
  `GiveReward(..., rewardCount: 1000)`을 한 번 호출
- 확률에 따라 서로 다른 `rewardConfirmId`가 나온다면
  추첨만 1,000번 수행하고 `rewardConfirmId`별 횟수를 집계한 뒤, 서로 다른 보상 종류별로 한 번씩 호출

예:

```text

Reward B: 310회
Reward C: 170회

GiveReward(B, rewardCount: 310)
GiveReward(C, rewardCount: 170)
```

이 방식은 기존 확률 결과를 유지하면서 `GiveReward()` 호출을 1,000회에서 보상 종류 수만큼으로 줄일 수 있습니다.

## 슬롯 계산 시 추가로 고려할 사항

단순히 “인벤토리에 해당 Item ID가 존재하는가”만 확인하면 부족합니다.

- 기존 스택이 최대 수량에 가까운 경우
- 보상 총수량이 최대 스택을 초과하는 경우
- 스택 불가능한 아이템
- 기간제 등 같은 Item ID여도 합칠 수 없는 아이템
- 재화처럼 인벤토리 슬롯을 사용하지 않는 아이템
- 상자를 전부 사용하면서 상자 슬롯 자체가 비워지는 경우

필요 슬롯은 다음 방식으로 계산해야 합니다.

```text
필요 슬롯
= ceil(
    (총 지급 수량 - 기존 호환 스택의 여유 수량)
    / 최대 스택 수량
  )
```

또한 상자를 모두 사용하여 원본 상자 슬롯이 사라진다면 그 슬롯도 가용 슬롯에 포함해야 합니다. 그렇지 않으면 실제로 지급 가능한데도 인벤토리 부족으로 처리할 수 있습니다.

## 최종 권고

가장 적절한 구현 순서는 다음과 같습니다.

1. 기존 확률 방식대로 보상 결과만 결정합니다.
2. 결과를 `rewardConfirmId` 또는 아이템별로 집계합니다.
3. 임시 집계 결과를 사용해 필요 슬롯을 한 번 계산합니다.
4. 공간이 부족하면 아이템을 사용하지 않고 에러를 반환합니다.
5. 공간이 충분하면 `rewardCount`를 사용해 종류별로 일괄 지급합니다.
6. 모든 사전 검사가 성공한 뒤 상자를 차감합니다.

`count=0` 아이템을 실제 인벤토리에 넣는 방식보다 수정량이 약간 늘 수 있지만, 기존 아이템 불변조건을 깨뜨리지 않고 성능과 정합성을 함께 해결할 수 있습니다. 특히 기존 `rewardCount` 기능을 활용하면 실제 변경 범위도 크지 않을 것으로 판단됩니다.

`Parallel.ForEach`를 호출해도 Zone Thread가 즉시 다음 틱을 처리하는 것은 아닙니다. 모든 병렬 작업이 끝날 때까지 호출한 Zone Thread가 기다리므로 특권 보상 메일처럼 비동기 처리되는 구조가 아닙니다.

여러 사용자가 동시에 실행하면 다음 문제도 생길 수 있습니다.

- ThreadPool 작업 증가
- 인벤토리 Dictionary 스냅샷을 동시에 생성
- 전체 CPU 및 메모리 대역폭 경쟁
- 다른 서버 비동기 작업의 ThreadPool 지연
- Zone Thread는 결과를 기다리므로 틱 지연 가능성은 여전히 존재

`Interlocked.Add()`는 `totalItemCount`만 보호합니다. 내부에서 접근하는 `ItemEntity`, DataManager 및 인벤토리 상태 전체의 병렬 안전성을 보장하지는 않습니다.
