### 1. 존 이동 중 변경 전 DB 정보를 가져올 수 있는가?

정상적인 의도는 다음 순서입니다.

1. 존 이탈로 `ZoneLeaveWait` 상태 전환
2. 기존 Actor 제거 과정에서 `SaveToDb(... needForceUpdate: true)` 호출
3. DBNode가 저장 완료 후 `SC_ZMQ_SaveToDB` 반환
4. 성공 응답을 받은 뒤 `GameUserRemoveAndLeaveZone` 실행
5. Gateway가 다음 존으로 이동
6. 다음 존의 `BindZone()`에서 `CS_ZMQ_QueryActorData`로 데이터 재조회

최종 저장은 [ActorUserModel.cs](E:/Rasalas/Trunk/qa/Server/EgonServer/ServerNodes/GameNode/Models/Actor/ActorUserModel.cs:88)에서 호출되고, 성공 응답을 받은 뒤에만 사용자 제거 명령을 등록하도록 되어 있습니다. [RepHandler.cs](E:/Rasalas/Trunk/qa/Server/EgonServer/ServerNodes/GameNode/PacketHandler/RepHandler.cs:120)

하지만 다음 경쟁 조건이 존재합니다.

- 사용자는 15초마다 주기적으로 `CS_ZMQ_SaveToDB`를 전송합니다.
- 존 이동으로 상태가 `ZoneLeaveWait`로 바뀐 시점에, 이전 주기 저장의 성공 응답이 도착할 수 있습니다.
- `SC_ZMQ_SaveToDB`에는 저장 요청을 구분할 `requestId`, `sequence`, `isFinalSave`가 없습니다. [ZmqSaveToDB.cs](E:/Rasalas/Trunk/qa/Server/EgonServer/Packet/Protocol/ZmqSaveToDB.cs:252)
- 응답 핸들러는 단순히 사용자 상태가 dispose 가능한지만 확인하고 사용자를 제거합니다.
- `ZoneLeaveWait`는 dispose 가능한 상태에 포함됩니다. [UserGameModel.cs](E:/Rasalas/Trunk/qa/Server/EgonServer/ServerNodes/GameNode/Models/User/UserGameModel.cs:30)

따라서 다음 순서가 코드상 배제되지 않습니다.

```text
주기 저장 A 전송
→ 존 이동 시작, ZoneLeaveWait
→ 저장 A 성공 응답 도착
→ 이를 “존 이동 최종 저장 완료”로 오인
→ 다음 존 이동 및 QueryActorData
→ 최종 저장 B가 아직 미처리
```

이 경우 다음 존에서 A 시점의 데이터를 가져올 수 있습니다.

### 2. 앱 강제 종료 후 DB 저장 실패 시 처리

앱이나 프로그램이 종료되면 서버의 로그아웃/Actor 제거 경로에서 강제 저장을 시도합니다.

```csharp
SaveToDb(eCheckCurrency.UserDisconnect, needForceUpdate: true);
```

DBNode에서는 다음 실패를 `SC_ZMQ_SaveToDB`로 반환합니다.

- DBController 없음: `InvalidUserState`
- 접속 정보 검증 실패: `HackingUser`
- 실제 DB 업데이트 실패: `FailUpdateDB`
- 캐시 포함 업데이트 실패: `FailedUpdateActorData`

관련 처리는 [DBHandler.cs](E:/Rasalas/Trunk/qa/Server/EgonServer/ServerNodes/DBNode/PacketHandler/DBHandler.cs:872)에 있습니다.

GameNode가 실패 응답을 받으면 로그를 남기고 `KickGraceful()`을 호출합니다. [RepHandler.cs](E:/Rasalas/Trunk/qa/Server/EgonServer/ServerNodes/GameNode/PacketHandler/RepHandler.cs:113)

그러나 현재 경로에는 다음 처리가 없습니다.

- 실패한 저장 패킷 재시도
- DB 실패 응답 시 `RollbackDBState()`
- 실패 데이터를 별도 큐나 durable outbox에 보관
- 실패한 사용자의 재로그인 전 복구 처리
- 응답이 오지 않을 때의 application-level ACK 타임아웃

`RollbackDBState()`는 `SendZMQ()`가 즉시 `false`를 반환한 경우에만 호출됩니다. [ActorUserModel.cs](E:/Rasalas/Trunk/qa/Server/EgonServer/ServerNodes/GameNode/Models/Actor/ActorUserModel.cs:3475) 실제 DBNode가 패킷을 받은 뒤 저장에 실패한 경우에는 호출되지 않습니다.

따라서 강제 종료 시 최종 저장까지 실패하면:

- 사용자 세션은 Kick/정리됩니다.
- 마지막 저장 이후 변경 데이터는 메모리와 함께 유실될 수 있습니다.
- 응답 자체가 오지 않으면 이 코드 경로만으로는 재시도나 확실한 정리가 보장되지 않습니다.
- 앞서 설명한 이전 저장 응답 경쟁 조건으로 사용자가 먼저 제거되면, 나중에 도착한 최종 저장 실패 응답은 `userModel == null`로 무시될 수도 있습니다.

추가로 계정 DB 저장인 `UpdateGlobalUserDataByDBAsync()`의 반환값은 무시됩니다. [DBHandler.cs](E:/Rasalas/Trunk/qa/Server/EgonServer/ServerNodes/DBNode/PacketHandler/DBHandler.cs:889) 따라서 계정 귀속 데이터 저장이 실패했는데도 Game DB 저장만 성공하면 전체 응답이 `Success`가 될 가능성도 있습니다.

권장 보완 사항은 다음과 같습니다.

- `CS/SC_ZMQ_SaveToDB`에 사용자별 단조 증가 `saveSequence` 추가
- 존 이동/로그아웃 시 `finalSaveSequence`와 일치하는 성공 응답만 사용자 제거 조건으로 인정
- 사용자별 저장 요청 직렬화 또는 in-flight 저장 barrier 적용
- 최종 저장 실패 시 idempotent 재시도와 durable retry queue 적용
- 다음 존 최초 조회는 write endpoint 또는 갱신된 DB 캐시에서 수행
- 계정 DB 저장 결과도 전체 성공 여부에 포함
- 저장 성공 전에는 dirty state와 Actor 데이터를 반환/초기화하지 않도록 수명 관리

즉, 현재 구현은 정상 상황에서는 저장 성공 후 이동하도록 만들어져 있지만, 패킷 간 상관관계가 없어 존 이동 시점의 데이터 정합성을 완전히 보장하지는 못합니다.
