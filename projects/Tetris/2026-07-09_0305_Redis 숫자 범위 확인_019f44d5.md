### Assistant

실시간 랭킹이면 보통 Redis **Sorted Set(ZSET)** 의 `score` 범위를 보면 됩니다.

Redis `ZADD`의 `score`는 **double-precision floating point number**, 즉 64-bit 부동소수점입니다. Redis 문서상 `+inf`, `-inf`도 값으로 허용됩니다. ([redis.io](https://redis.io/docs/latest/commands/zadd/))

실무 기준으로는 이렇게 잡으면 됩니다.

- **정수 점수로 안전하게 쓰는 범위**: `-9,007,199,254,740,991` ~ `9,007,199,254,740,991`
- 이유: double은 53비트 정밀도라서 이 범위를 넘으면 `+1` 단위 점수가 정확히 구분되지 않을 수 있습니다.
- 이론상 double의 최대값은 훨씬 크지만, 랭킹 점수처럼 “1점 차이”가 중요하면 `9e15` 아래로 두는 게 안전합니다.
- `score * 1_000_000 + timestamp` 같은 합성 점수는 쉽게 정밀도 범위를 넘을 수 있으니 조심해야 합니다.
- millisecond timestamp는 대략 `1.7e12`라 괜찮지만, nanosecond timestamp는 `1.7e18` 수준이라 ZSET score로는 위험합니다.

참고로 ZSET이 아니라 `INCR`/`INCRBY`로 단순 카운터를 쓴다면 Redis는 **signed 64-bit integer** 범위로 제한됩니다:  
`-9,223,372,036,854,775,808` ~ `9,223,372,036,854,775,807` ([redis.io](https://redis.io/docs/latest/commands/incr/))

결론: **랭킹 점수는 ZSET score에 넣되, 정수 점수라면 ±9,007조 정도 안에서 설계**하는 게 가장 깔끔합니다. 같은 점수일 때는 Redis가 member 문자열 기준으로 정렬하니, 동점 처리 정책도 따로 정해두는 게 좋습니다. ([redis.io](https://redis.io/docs/latest/develop/data-types/sorted-sets/))

### Assistant

결론부터 말하면:

`exp BIGINT(20) NOT NULL` 값은 **Redis에 저장/표시는 가능합니다.**  
다만 그 값을 **Redis ZSET의 score로 그대로 써서 정확한 랭킹**을 만들 수 있는지는 제한이 있습니다.

MySQL `BIGINT(20)`은 `UNSIGNED`가 없으면 signed BIGINT라서 범위가:

```text
-9,223,372,036,854,775,808
~
 9,223,372,036,854,775,807
```

여기서 `(20)`은 표시 폭 개념이고, 실제 저장 범위를 늘려주는 의미는 아닙니다.

Redis에서 가능한 경우는 이렇게 나뉩니다.

```text
Redis String / Hash 값으로 저장:
가능. BIGINT 값을 문자열처럼 정확히 저장 가능.

Redis INCRBY 같은 정수 연산:
signed 64-bit 범위라서 MySQL signed BIGINT와 거의 맞음.

Redis Sorted Set score로 랭킹:
주의 필요. score는 double이라서 정수는 대략 ±9,007,199,254,740,991 까지만 1 단위로 안전.
```

즉 `exp`가 `9,007,199,254,740,991` 이하로 절대 안 넘는다면:

```redis
ZADD ranking 123456789 user:1001
```

이렇게 써도 괜찮습니다.

하지만 `exp`가 MySQL BIGINT 최대치 근처까지 갈 수 있다면 ZSET score에 그대로 넣으면 안 좋습니다. 예를 들어 `9223372036854775806`과 `9223372036854775807` 같은 값은 Redis score에서 정확히 구분되지 않을 수 있습니다.

실무 추천은 이겁니다.

```text
1. 게임/서비스 정책상 exp 최대값이 9e15 이하라면:
   ZSET score = exp 로 사용해도 OK.

2. exp가 BIGINT 전체 범위까지 가능해야 한다면:
   Redis에는 정확한 exp를 Hash/String으로 저장하고,
   랭킹용 ZSET은 별도 인코딩 방식이나 DB 기준 정렬을 사용.
```

BIGINT 전체 범위까지 정확한 Redis 랭킹이 필요하면 `score` 대신 member를 고정 폭 문자열로 만드는 방식도 가능합니다. 예를 들어 경험치가 음수가 아니라면:

```text
member = 0000000000000012345:userId
score = 0
```

처럼 넣고 lex 정렬을 쓰는 방식입니다. 단, 업데이트할 때 기존 member를 지워야 해서 `userId -> old member` 매핑을 같이 관리해야 합니다.

정리하면, **Redis에 BIGINT 값을 저장하는 건 가능**하지만, **Sorted Set score로 MySQL BIGINT 전체 범위를 정확히 랭킹 처리하는 건 제한이 있습니다.** 경험치 최대값이 9007조 이하인지가 핵심 기준입니다.
