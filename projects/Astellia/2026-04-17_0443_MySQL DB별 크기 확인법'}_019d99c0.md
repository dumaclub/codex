### Assistant

MySQL에서 DB별 용량(MB)은 `information_schema.TABLES`로 확인하는 게 가장 일반적입니다.

```sql
SELECT
    table_schema AS db_name,
    ROUND(SUM(data_length + index_length) / 1024 / 1024, 2) AS size_mb
FROM information_schema.TABLES
WHERE table_schema NOT IN ('mysql', 'information_schema', 'performance_schema', 'sys')
GROUP BY table_schema
ORDER BY size_mb DESC;
```

특정 DB만 보고 싶으면:

```sql
SELECT
    table_schema AS db_name,
    ROUND(SUM(data_length + index_length) / 1024 / 1024, 2) AS size_mb
FROM information_schema.TABLES
WHERE table_schema = '내DB명'
GROUP BY table_schema;
```

접속 후 실행 예시는 이렇게 하시면 됩니다.

```bash
mysql -u 사용자명 -p
```

참고로 이 값은 테이블 데이터(`data_length`) + 인덱스(`index_length`) 기준이라, 실제 OS 디스크 사용량과는 조금 차이날 수 있습니다.

### Assistant

복원 자체는 가능합니다. `37GB`라는 이유만으로 MySQL이 복원을 못 하지는 않습니다. 다만 운영 이관 관점에서는 `문제 없다`기보다 `너무 큰 배치라 리스크가 크다` 쪽에 가깝습니다.

지금 쿼리는 `idx >= 2000000000` 이라서 사실상 `약 3.5억 건`을 한 번에 덤프한 상태입니다. 그래서 이 파일 1개가 커진 거고, 이런 단위는 아래 이유로 권장하지 않습니다.

- 복원 중 실패하면 그 큰 구간을 처음부터 다시 해야 합니다.
- 대상 DB에서 적재 시간이 오래 걸립니다. 인덱스가 많아서 더 느릴 수 있습니다.
- 대상 서버 디스크는 `37GB 파일 크기`만 보면 안 되고, 실제 적재될 테이블/인덱스 공간 + redo/binlog 여유까지 봐야 합니다.
- `--no-create-info` 옵션을 썼으니 대상 DB에 **동일한 테이블 구조**가 먼저 있어야 합니다.
- 대상 DB가 binlog를 쓰는 환경이면, 적재하면서 binlog도 많이 쌓일 수 있습니다.

특히 이 테이블은 `InnoDB`라서 `--disable-keys=0` 같은 옵션은 큰 의미가 없습니다. MyISAM 쪽 효과가 더 큽니다.

가장 실무적으로는 `37GB 한 파일` 복원보다 `idx 500만` 또는 `1000만` 단위로 잘라서 덤프/복원하는 게 훨씬 안전합니다.  
지금 샘플 기준으로 보면 `500만 건`이면 파일이 대략 `수백 MB ~ 1GB 내외` 수준으로 내려갈 가능성이 커서 다루기 훨씬 편합니다.

### Assistant

구조 자체는 맞습니다. 다만 그대로 운영에 쓰기엔 몇 군데 꼭 고치시는 게 좋습니다.

1. 지금 스크립트는 실패 감지가 없습니다. `mysqldump`나 `mysql`이 중간에 실패해도 다음 chunk로 넘어갈 수 있어서, 부분 이관 상태를 놓치기 쉽습니다.

3. `--skip-opt`는 굳이 안 쓰는 편이 낫습니다. 필요한 기본 옵션들까지 꺼져서 문자셋/기타 동작이 애매해질 수 있습니다.
4. 운영 DB 이관이면 chunk마다 `건수 검증`은 꼭 넣는 게 안전합니다.
5. 현재 방식은 `초기 전체 복사`까지만 처리합니다. 운영 중 신규 데이터는 마지막에 `delta 이관`을 한 번 더 해야 합니다.
6. 비밀번호를 스크립트에 평문으로 넣으면 `ps` 등에서 노출될 수 있습니다.

실무 기준으로는 아래처럼 조금 바꿔서 쓰는 걸 추천드립니다.

```bash
#!/bin/bash
set -Eeuo pipefail

SRC_HOST="10.0.100.7"
SRC_USER="admin"
SRC_PWD="password"
SRC_DB="rasalas_global"
TABLE="gamelog_partition"

TGT_HOST="타겟_DB_IP"
TGT_USER="admin"
TGT_PWD="password"
TGT_DB="타겟_DB명"

START_IDX=1
MAX_IDX=2354941336
CHUNK_SIZE=5000000

WORKDIR="/data/mysql_mig"
mkdir -p "$WORKDIR"

echo "마이그레이션 시작: $(date)"

while [ "$START_IDX" -le "$MAX_IDX" ]; do
    END_EXCL=$((START_IDX + CHUNK_SIZE))
    if [ "$END_EXCL" -gt $((MAX_IDX + 1)) ]; then
        END_EXCL=$((MAX_IDX + 1))
    fi
    END_INCL=$((END_EXCL - 1))

    FILE="$WORKDIR/${TABLE}_${START_IDX}_${END_INCL}.sql.gz"

    echo "Dumping idx: $START_IDX ~ $END_INCL"

    mysqldump -h "$SRC_HOST" -u "$SRC_USER" -p"$SRC_PWD" \
        --single-transaction \
        --quick \
        --no-create-info \
        --extended-insert \
        --set-gtid-purged=OFF \
        --order-by-primary \
        --default-character-set=utf8mb3 \
        --where="idx >= $START_IDX AND idx < $END_EXCL" \
        "$SRC_DB" "$TABLE" | gzip -1 > "$FILE"

    SRC_CNT=$(mysql -N -s -h "$SRC_HOST" -u "$SRC_USER" -p"$SRC_PWD" \
        -e "SELECT COUNT(*) FROM ${SRC_DB}.${TABLE} WHERE idx >= $START_IDX AND idx < $END_EXCL")

    echo "Loading idx: $START_IDX ~ $END_INCL"
    gunzip -c "$FILE" | mysql -h "$TGT_HOST" -u "$TGT_USER" -p"$TGT_PWD" "$TGT_DB"

    TGT_CNT=$(mysql -N -s -h "$TGT_HOST" -u "$TGT_USER" -p"$TGT_PWD" \
        -e "SELECT COUNT(*) FROM ${TGT_DB}.${TABLE} WHERE idx >= $START_IDX AND idx < $END_EXCL")

    if [ "$SRC_CNT" -ne "$TGT_CNT" ]; then
        echo "건수 불일치 발생: $START_IDX ~ $END_INCL (SRC=$SRC_CNT, TGT=$TGT_CNT)"
        exit 1
    fi

    echo "완료: $START_IDX ~ $END_INCL (COUNT=$SRC_CNT)"
    START_IDX=$END_EXCL
done

echo "초기 마이그레이션 완료: $(date)"
```

이렇게 바꾼 이유는 단순합니다.

- `set -Eeuo pipefail`로 실패 시 즉시 중단
- chunk 파일을 범위별로 따로 저장해서 재시도 가능
- `gzip`으로 파일 크기 절감
- source/target `COUNT(*)` 비교로 최소 검증 수행
- `END_INCL`, `END_EXCL`를 분리해서 범위 혼동 방지

추가로 꼭 기억하실 점은 이것입니다.

- 이 스크립트는 `MAX_IDX` 시점까지만 복사합니다.
- 운영 중에는 그 뒤에 들어온 데이터가 있으니, 초기 완료 후 `MAX_IDX+1 ~ 새 MAX_IDX`를 한 번 더 돌려야 합니다.
- 마지막에는 짧게 쓰기 중지 후 최종 delta만 반영하고 컷오버하는 게 안전합니다.

그리고 가능하면 `5,000,000`건으로 바로 시작하지 말고, 먼저 `500,000` 또는 `1,000,000`건으로 한 번 테스트해서 `덤프 시간`, `복원 시간`, `파일 크기`, `DB 부하`를 보고 chunk 크기를 확정하는 걸 권장드립니다.

**2. 백업 스크립트: `01_dump_chunks.sh`**
```bash
#!/bin/bash
set -Eeuo pipefail

SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"
. "$SCRIPT_DIR/mig.conf"

mkdir -p "$DUMP_DIR" "$STATE_DIR" "$LOG_DIR"

LOG_FILE="$LOG_DIR/dump_$(date +%F_%H%M%S).log"
STATE_FILE="$STATE_DIR/dumped.list"
touch "$STATE_FILE"

CUR_START="${1:-$START_IDX}"
CUR_MAX="${2:-$MAX_IDX}"

echo "[START] dump $(date) start=$CUR_START max=$CUR_MAX chunk=$CHUNK_SIZE" | tee -a "$LOG_FILE"

while [ "$CUR_START" -le "$CUR_MAX" ]; do
    END_IDX=$((CUR_START + CHUNK_SIZE - 1))
    if [ "$END_IDX" -gt "$CUR_MAX" ]; then
        END_IDX="$CUR_MAX"
    fi

    FILE="$(printf "%s/%s_%010d_%010d.sql.gz" "$DUMP_DIR" "$TABLE" "$CUR_START" "$END_IDX")"

    if grep -qxF "$FILE" "$STATE_FILE"; then
        echo "[SKIP] already dumped $FILE" | tee -a "$LOG_FILE"
        CUR_START=$((END_IDX + 1))
        continue
    fi

    echo "[DUMP] idx $CUR_START ~ $END_IDX -> $FILE" | tee -a "$LOG_FILE"

    mysqldump -h "$SRC_HOST" -P "$SRC_PORT" -u "$SRC_USER" -p"$SRC_PWD" \
        --single-transaction \
        --quick \
        --skip-lock-tables \
        --no-create-info \
        --extended-insert \
        --skip-add-locks \
        --skip-disable-keys \
        --set-gtid-purged=OFF \
        --order-by-primary \
        --default-character-set=utf8mb3 \
        --where="idx >= $CUR_START AND idx <= $END_IDX" \
        "$SRC_DB" "$TABLE" | gzip -1 > "$FILE"

    SRC_CNT=$(mysql -N -s -h "$SRC_HOST" -P "$SRC_PORT" -u "$SRC_USER" -p"$SRC_PWD" \
        -e "SELECT COUNT(*) FROM \`${SRC_DB}\`.\`${TABLE}\` WHERE idx >= $CUR_START AND idx <= $END_IDX")

    FILE_SIZE=$(du -h "$FILE" | awk '{print $1}')
    echo "[DONE] idx $CUR_START ~ $END_IDX count=$SRC_CNT file_size=$FILE_SIZE" | tee -a "$LOG_FILE"

    echo "$FILE" >> "$STATE_FILE"
    CUR_START=$((END_IDX + 1))
done

echo "[END] dump $(date)" | tee -a "$LOG_FILE"
```

**3. 복원 스크립트: `02_restore_chunks.sh`**
```bash

SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"

mkdir -p "$STATE_DIR" "$LOG_DIR"

LOG_FILE="$LOG_DIR/restore_$(date +%F_%H%M%S).log"
STATE_FILE="$STATE_DIR/loaded.list"
touch "$STATE_FILE"

shopt -s nullglob
FILES=( "$DUMP_DIR"/${TABLE}_*.sql.gz )

if [ ${#FILES[@]} -eq 0 ]; then
    echo "No dump files found in $DUMP_DIR"
    exit 1
fi

echo "[START] restore $(date)" | tee -a "$LOG_FILE"

for FILE in "${FILES[@]}"; do
    if grep -qxF "$FILE" "$STATE_FILE"; then

        continue

    echo "$FILE" >> "$STATE_FILE"
    echo "[DONE] $(basename "$FILE")" | tee -a "$LOG_FILE"
```

### User

왜 .gz 으로 압축하나요?

### Assistant

`.gz`로 압축하는 이유는 **덤프 파일이 SQL 텍스트라서 압축이 아주 잘 되기 때문**입니다.

특히 `mysqldump` 결과물은 이런 특징이 있습니다.

- `INSERT INTO ...` 같은 반복 문자열이 많음
- 숫자/문자 데이터가 줄 단위로 계속 반복됨
- 텍스트 기반이라 gzip 압축 효율이 높음

그래서 장점이 큽니다.

- 디스크 사용량 감소
- 다른 서버로 복사할 때 전송량 감소
- 백업 파일 보관이 쉬움
- `gunzip -c file.sql.gz | mysql ...` 처럼 **풀지 않고 바로 복원 가능**

예를 들어 지금처럼 덤프가 `37GB`면, gzip 하면 데이터 성격에 따라 꽤 많이 줄 수 있습니다.  
로그성 테이블은 보통 압축 효과가 괜찮은 편입니다.

다만 단점도 있습니다.

- 압축/해제에 CPU를 더 씀
- 바로 `vi`나 `less`로 열어보기는 불편함
- CPU가 아주 바쁜 서버라면 압축이 오히려 부담일 수 있음

그래서 정리하면:

- **네트워크로 옮겨야 한다** → `.gz` 추천
- **파일이 너무 크다** → `.gz` 추천
- **같은 서버 내 임시 작업이고 CPU가 아깝다** → 압축 없이 `.sql`도 가능

제가 예시에서 `gzip -1`을 넣은 건 **압축률보다 속도를 우선**한 설정입니다.  
대용량 이관에서는 보통 최고압축보다 `빠른 압축`이 더 실용적입니다.

원하시면 다음 답변에서
- `.sql`로 할 때
- `.sql.gz`로 할 때

각각의 백업/복원 명령 차이만 딱 비교해서 정리해드릴게요.

**2. 백업 스크립트: `01_dump_chunks.sh`**
```bash
#!/bin/bash
set -Eeuo pipefail

SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"
. "$SCRIPT_DIR/mig.conf"

mkdir -p "$DUMP_DIR" "$STATE_DIR" "$LOG_DIR"

LOG_FILE="$LOG_DIR/dump_$(date +%F_%H%M%S).log"
STATE_FILE="$STATE_DIR/dumped.list"
touch "$STATE_FILE"

CUR_START="${1:-$START_IDX}"
CUR_MAX="${2:-$MAX_IDX}"

echo "[START] dump $(date) start=$CUR_START max=$CUR_MAX chunk=$CHUNK_SIZE" | tee -a "$LOG_FILE"

while [ "$CUR_START" -le "$CUR_MAX" ]; do
    END_IDX=$((CUR_START + CHUNK_SIZE - 1))
    if [ "$END_IDX" -gt "$CUR_MAX" ]; then
        END_IDX="$CUR_MAX"
    fi

    FILE="$(printf "%s/%s_%010d_%010d.sql" "$DUMP_DIR" "$TABLE" "$CUR_START" "$END_IDX")"

    if grep -qxF "$FILE" "$STATE_FILE"; then
        echo "[SKIP] already dumped $FILE" | tee -a "$LOG_FILE"
        CUR_START=$((END_IDX + 1))
        continue
    fi

    echo "[DUMP] idx $CUR_START ~ $END_IDX -> $FILE" | tee -a "$LOG_FILE"

    mysqldump -h "$SRC_HOST" -P "$SRC_PORT" -u "$SRC_USER" -p"$SRC_PWD" \
        --single-transaction \
        --quick \
        --skip-lock-tables \
        --no-create-info \
        --extended-insert \
        --skip-add-locks \
        --skip-disable-keys \
        --set-gtid-purged=OFF \
        --order-by-primary \
        --default-character-set=utf8mb3 \
        --where="idx >= $CUR_START AND idx <= $END_IDX" \
        "$SRC_DB" "$TABLE" > "$FILE"

    SRC_CNT=$(mysql -N -s -h "$SRC_HOST" -P "$SRC_PORT" -u "$SRC_USER" -p"$SRC_PWD" \
        -e "SELECT COUNT(*) FROM \`${SRC_DB}\`.\`${TABLE}\` WHERE idx >= $CUR_START AND idx <= $END_IDX")

    FILE_SIZE=$(du -h "$FILE" | awk '{print $1}')
    echo "[DONE] idx $CUR_START ~ $END_IDX count=$SRC_CNT file_size=$FILE_SIZE" | tee -a "$LOG_FILE"

    echo "$FILE" >> "$STATE_FILE"
    CUR_START=$((END_IDX + 1))
done

echo "[END] dump $(date)" | tee -a "$LOG_FILE"
```

### User

복원하려는 DB에 binlog 가 남는지 확인하는 방법을 알려주세요.

### Assistant

복원 시 binlog가 실제로 쌓이는지 확인하는 방법을 공식 기준으로 빠르게 확인해보겠습니다. 운영 반영 전에 확인 포인트와 주의할 점까지 같이 정리해드릴게요.

### Assistant

확인은 3단계로 보시면 됩니다.

1. 서버 자체에서 binlog가 켜져 있는지
```sql
SHOW VARIABLES LIKE 'log_bin';
SHOW VARIABLES LIKE 'log_bin_basename';
```

- `log_bin = ON` 이면 서버가 binary log를 쓰는 상태입니다.
- `log_bin = OFF` 이면 복원해도 binlog는 남지 않습니다.

2. 이번 복원 세션이 binlog를 쓰는지
```sql
SHOW SESSION VARIABLES LIKE 'sql_log_bin';
```

- `sql_log_bin = ON` 이면 현재 세션의 `INSERT/UPDATE/DELETE`가 binlog에 기록됩니다.
- `sql_log_bin = OFF` 이면 현재 세션은 binlog를 남기지 않습니다.
- 단, 이 값은 `log_bin=ON`일 때만 의미가 있습니다.

3. 실제 binlog 파일이 늘어나는지
```sql
SHOW BINARY LOGS;
```

이걸 복원 전/후에 각각 실행해서 마지막 binlog 파일의 `File_size`가 커졌는지 보면 됩니다.  
커졌거나 새 binlog 파일이 생기면, 복원 작업이 binlog를 남긴 것입니다.

실무적으로는 이렇게 확인하면 가장 확실합니다.

```sql
SHOW VARIABLES LIKE 'log_bin';
SHOW SESSION VARIABLES LIKE 'sql_log_bin';
SHOW BINARY LOGS;
```

그 다음 아주 작은 테스트 chunk 하나만 복원한 뒤 다시:

```sql
SHOW BINARY LOGS;
```

마지막 파일 크기가 증가하면 binlog가 쌓인 겁니다.

추가로 자동 삭제 설정도 같이 확인해두시면 좋습니다.

```sql
SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';
SHOW VARIABLES LIKE 'expire_logs_days';
```

- `binlog_expire_logs_seconds` 는 자동 purge 보관 기간입니다.
- 구버전에서는 `expire_logs_days` 를 보는 경우가 있습니다.

덤프 파일 자체도 확인할 수 있습니다.  
파일 안에 이런 구문이 있으면 복원 세션에서 binlog를 끄도록 시도합니다.


```bash
#!/bin/bash
set -Eeuo pipefail

SCRIPT_DIR="$(cd "$(dirname "$0")" && pwd)"
. "$SCRIPT_DIR/mig.conf"

mkdir -p "$STATE_DIR" "$LOG_DIR" "$STATE_DIR/loaded_ok" "$STATE_DIR/loaded_fail"

LOG_FILE="$LOG_DIR/restore_$(date +%F_%H%M%S).log"
MAX_PARALLEL=5

shopt -s nullglob
FILES=( "$DUMP_DIR"/${TABLE}_*.sql )

if [ ${#FILES[@]} -eq 0 ]; then
    echo "No dump files found in $DUMP_DIR"
    exit 1
fi

restore_one() {
    local FILE="$1"
    local BASE
    BASE="$(basename "$FILE")"

    if [ -f "$STATE_DIR/loaded_ok/${BASE}.ok" ]; then
        echo "[SKIP] already loaded $BASE" | tee -a "$LOG_FILE"
        return 0
    fi

    echo "[LOAD] $BASE" | tee -a "$LOG_FILE"

    if mysql -h "$TGT_HOST" -P "$TGT_PORT" -u "$TGT_USER" -p"$TGT_PWD" "$TGT_DB" < "$FILE"; then
        touch "$STATE_DIR/loaded_ok/${BASE}.ok"
        echo "[DONE] $BASE" | tee -a "$LOG_FILE"
        return 0
    else
        touch "$STATE_DIR/loaded_fail/${BASE}.fail"
        echo "[FAIL] $BASE" | tee -a "$LOG_FILE"
        return 1
    fi
}

echo "[START] restore $(date), parallel=$MAX_PARALLEL" | tee -a "$LOG_FILE"

running=0

for FILE in "${FILES[@]}"; do
    restore_one "$FILE" &
    running=$((running + 1))

    if [ "$running" -ge "$MAX_PARALLEL" ]; then
        wait -n
        running=$((running - 1))
    fi
done

wait

if compgen -G "$STATE_DIR/loaded_fail/*.fail" > /dev/null; then
    echo "[END] restore finished with failures $(date)" | tee -a "$LOG_FILE"
    exit 1
fi

echo "[END] restore completed successfully $(date)" | tee -a "$LOG_FILE"
```

이 스크립트 특징은:

- 동시에 최대 `5개` 실행
- 성공한 파일은 `loaded_ok/*.ok`
- 실패한 파일은 `loaded_fail/*.fail`
- 실패한 chunk만 따로 재시도 가능
