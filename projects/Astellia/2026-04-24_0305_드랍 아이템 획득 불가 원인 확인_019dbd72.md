Router가 `port + i`로 여러 개 바인딩되고 각 Poller가 `PacketProcessForZMQ`를 호출할 수 있게 될 뿐입니다. 참고: [ServerController.cs](E:/ProjectA02/Trunk/Dev/Server/EgonServer/Controllers/ServerController.cs:274), [ServerModule.cs](E:/ProjectA02/Trunk/Dev/Server/EgonServer/Server/ServerModule.cs:1196)

동기화는 “모든 기능에 무조건 추가”라기보다, 원칙적으로 아래 둘 중 하나가 필요합니다.

- 패킷 핸들러는 상태를 직접 만지지 않고 전부 `AddCommand()`로 소유 워커 큐에 넣는다. 이 경우 `ConcurrentQueue`가 멀티 Poller producer를 받아주고, 실제 상태 변경은 기존처럼 단일 워커에서 직렬 처리됩니다.
- 핸들러에서 직접 Manager 상태를 읽거나 변경하는 코드는 별도 lock, Concurrent 컬렉션, owner-thread 위임이 필요합니다. 현재 `CommunityHandler`에는 `AddCommand()` 없이 직접 실행하는 경로가 꽤 있습니다. 예: 스케줄/대기열/월드던전/검색/길드 알림/랭킹 치트/제작 제한 등.

중요한 함정도 있습니다. `NETMQ_TH_USE`에서 Community의 `CustomThreadCount`만 늘려도 송신 쪽은 Community 대상 포트를 자동 분산하지 않습니다. `SendController.AddServer()`의 멀티 포트 연결은 사실상 Game/Gateway 간 zone socket 용도로만 열려 있고, 그 외 타입은 여러 DealerSocket을 만들어도 기본 `port`에 붙습니다. 참고: [SendController.cs](E:/ProjectA02/Trunk/Dev/Server/EgonServer/Controllers/SendController.cs:35), [ServerController.cs](E:/ProjectA02/Trunk/Dev/Server/EgonServer/Controllers/ServerController.cs:2189), [ServerController.cs](E:/ProjectA02/Trunk/Dev/Server/EgonServer/Controllers/ServerController.cs:2228)

스레드 할당 흐름은 이렇게 보면 됩니다.

- 서버 시작 시 `ServerController`가 서버 타입으로 `CustomThreadCount`를 결정합니다.
- `BindRouter()`가 `CustomThreadCount`만큼 Router/Poller를 만들고 동일한 `PacketProcessForZMQ`를 연결합니다.
- `PacketProcessForZMQ()`는 Poller 스레드에서 패킷을 파싱하고 `DispatchPacketForZMQ()`를 호출합니다.
- 일반 ZMQ 패킷은 DB 서버가 아니면 핸들러가 Poller 스레드에서 직접 호출됩니다. 참고: [ServerModule.cs](E:/ProjectA02/Trunk/Dev/Server/EgonServer/Server/ServerModule.cs:1914)
- 커뮤니티 핸들러 대부분은 `CommunityWorkerManager.Instance.AddCommand(cmd)` 같은 식으로 기능별 워커 큐에 넘깁니다.
- `ThreadModel.Start()`가 실제 OS Thread를 만들고, 각 워커의 `ProcessUpdate()`가 큐를 비우며 로직을 실행합니다. 참고: [ThreadModel.cs](E:/ProjectA02/Trunk/Dev/Server/EgonServer/Models/ThreadModel.cs:31), [ThreadModel_CommunityWorker.cs](E:/ProjectA02/Trunk/Dev/Server/EgonServer/ServerNodes/CommunityNode/Thread/ThreadModel_CommunityWorker.cs:36)

결론적으로 Community의 병렬화를 하려면 `CustomThreadCount`만 올리는 방식은 효과도 제한적이고 위험합니다. 안전한 방향은 먼저 “ZMQ 핸들러는 무조건 command enqueue만 한다”는 구조로 정리한 뒤, 병목이 확인되는 기능만 `partyId`, `charId`, `guildId` 같은 owner key 기준으로 워커 샤딩하는 쪽입니다.
